# BPD — Big Project Done

**Фреймворк для проектов, которые не помещаются в одну сессию.**

Проект русскоязычный: команды, шаблоны и документация — на русском.

> **Версия 2.0.0.** Ставится как плагин Claude Code. Что работает, а чего нет —
> сказано ниже прямо, в разделе «Честные границы».

Вдохновлён [GSD (Get Shit Done)](https://github.com/gsd-build/get-shit-done),
но рассчитан на **любую** работу, а не только на код: книга, курс, исследование,
сайт, мероприятие.

## Что это решает

Большой проект в чате разваливается предсказуемо. Через неделю никто не помнит,
почему выбрали именно этот вариант. После `/clear` контекст пуст. К пятнадцатому
этапу модель тонет в собственной истории и начинает противоречить себе.

BPD выносит память проекта из чата в файлы:

```
разговор  ──► забывается при /clear, тонет к 15-му этапу
файлы     ──► переживают /clear, закрытый ноутбук и месяц простоя
```

- Проект режется на этапы; каждый планируется, выполняется и проверяется.
- Решения с обоснованием живут в файле, который никогда не стирается.
- Статус этапа **не хранится, а вычисляется** по файлам на диске — устареть
  он поэтому не может.
- Для больших проектов планировщик, исполнитель и проверщик работают каждый
  в свежем контексте, и проверяет тот, кто не видел, как делали.

## Установка

```
/plugin marketplace add vefmvai/claude-plugins
/plugin install bpd@vefmvai
/reload-plugins
```

Посмотреть, ничего не устанавливая:

```
git clone https://github.com/vefmvai/big-project-done.git
claude --plugin-dir ./big-project-done
```

Обновление — `/plugin update bpd@vefmvai`.

### Если стоял BPD 1.x

Версия 1.x ставилась скриптом `install.sh`, который раскладывал файлы по четырём
папкам `~/.claude/`. Пока они там лежат, у вас **две копии команд `/bpd:*`**,
и какая сработает — вопрос везения. Уберите старую:

```bash
bash scripts/remove-legacy-install.sh
```

Скрипт показывает, что нашёл, и спрашивает подтверждение. Рабочие папки `.bpd/`
внутри ваших проектов он не трогает: **формат `.bpd/` не менялся, старые проекты
работают дальше без переделки.**

## Быстрый старт

```
/bpd:start    — рассказать Claude о проекте
/bpd:plan     — получить план первого этапа
/bpd:do       — выполнить этап
/bpd:check    — проверить результат
```

Дальше `plan → do → check` по кругу. Полный список команд — `/bpd:help`
или [`references/commands.md`](references/commands.md).

Пользовательская инструкция без технических деталей — [GUIDE.md](GUIDE.md).

## Как устроено

```
big-project-done/
├── .claude-plugin/plugin.json   манифест плагина
├── skills/                      7 команд /bpd:* — каждая целиком в одном файле
├── agents/                      3 субагента: planner, executor, checker
├── templates/                   шаблоны файлов проекта
├── references/
│   ├── rules.md                 общие правила: статусы, пути, нумерация, дома фактов
│   └── commands.md              справка /bpd:help
└── scripts/                     уборка установки 1.x
```

В каждом проекте после `/bpd:start` появляется:

```
.bpd/
├── PROJECT.md   что за проект, рамки, решения — только дописывается
├── ROADMAP.md   дорожная карта: этапы, цели, критерии готовности
├── STATE.md     история, проблемы, следующий шаг — перезаписывается
├── config.json  настройки
└── stages/NN-imya/  PLAN.md · RESULT.md · CHECK.md
```

## Три принципа, на которых всё держится

**1. Один факт — один дом.** Значение живёт в одном файле; остальные его читают.
Поэтому в `ROADMAP.md` нет колонки «Статус» (её никто не обновляет — она обречена
протухнуть), а в `STATE.md` нет решений (файл, который стирают, — плохой дом
для того, что терять нельзя).

**2. Статус вычисляется, а не объявляется.** Статус этапа выводится из файлов
в его папке:

| В папке лежит | Статус |
|---|---|
| ничего | ○ Не начат |
| `PLAN.md`, все задачи `[ ]` | ◎ Спланирован |
| `PLAN.md`, часть задач `[x]` | ◐ В работе |
| `RESULT.md` | ● Выполнен |
| `CHECK.md` с итогом «Принято» | ✓ Принят |

Файлы создаёт сама работа, поэтому соврать они не могут. Отсюда жёсткое правило:
`RESULT.md` создаётся **только когда все задачи закрыты**.

**3. Номера этапов вечны.** Номер выдаётся один раз и не меняется никогда — он
записан в имени папки, в трёх файлах этапа и в истории. Перенумерация превратила
бы все эти записи в ссылки в никуда. Порядок выполнения задаёт порядок строк
в карте, а не номер, поэтому после правок номера могут идти вразнобой.

Полностью — [`references/rules.md`](references/rules.md). Это единственный дом
общих правил: команды его читают, а не пересказывают.

## Масштаб проекта

| Масштаб | Этапов | Как работает |
|---|---|---|
| Быстрый | 1–5 | план → выполнение, проверки нет |
| Средний | 5–15 | план → выполнение → проверка в текущем чате |
| Большой | 15+ | то же, но каждая роль — в свежем контексте |

Свежий контекст включается полем `use_subagents` в `.bpd/config.json`. Масштаб
задаёт умолчание, но не командует: можно включить субагентов и на среднем проекте.

## Честные границы

Проект обязан говорить о себе то, что требует от чужих.

- **BPD не делает работу за вас и не проверяет содержание.** Он следит за формой:
  все ли задачи закрыты, все ли заявленные файлы на месте, пройден ли чеклист.
  Хороша ли глава по существу — решает человек на шаге `/bpd:check`.
- **«Принято» не значит «хорошо».** Это значит «сделано то, что обещал план».
  Если план был плохим, приёмка это не поймает — для этого есть `/bpd:update`.
- **Свежий контекст стоит денег.** Субагент перечитывает `PROJECT.md`, карту
  и нужные `RESULT.md` при каждом запуске. На проекте из тридцати этапов это
  заметно. Ради этого он и существует, но платить приходится.
- **Ничего не проверяется машиной.** Валидатора папки `.bpd/` пока нет: все
  правила исполняются моделью по тексту, то есть это просьбы, а не гарантии.
  Механическая проверка — следующая большая задача.
- **Нет истории версий.** BPD не делает коммитов и не откатывает этапы.
  Если проект в git — коммитьте сами между этапами.
- **Проверено на macOS.** На Windows и Linux не проверялось. Плагин — это
  markdown-файлы без запускаемого кода, так что ломаться там нечему, кроме
  скрипта уборки `scripts/remove-legacy-install.sh`, которому нужен bash.
