# BPD — Big Project Done

**Фреймворк для проектов, которые не помещаются в одну сессию.**

Проект русскоязычный: команды, шаблоны и документация — на русском.

> **Версия 2.0.0.** Ставится как плагин Claude Code. Что работает, а чего нет —
> сказано ниже прямо, в разделе «Честные границы».

Вдохновлён [GSD (Get Shit Done)](https://github.com/gsd-build/get-shit-done),
но рассчитан на **любую** работу, а не только на код: книга, курс, исследование,
сайт, мероприятие.

## Что это решает

Большой проект в чате разваливается предсказуемо. Через неделю никто не помнит,
почему выбрали именно этот вариант. После `/clear` контекст пуст. К пятнадцатому
этапу модель тонет в собственной истории и начинает противоречить себе.

BPD выносит память проекта из чата в файлы:

```
разговор  ──► забывается при /clear, тонет к 15-му этапу
файлы     ──► переживают /clear, закрытый ноутбук и месяц простоя
```

- Проект режется на этапы; каждый планируется, выполняется и проверяется.
- Решения с обоснованием живут в файле, который никогда не стирается.
- Статус этапа **не хранится, а вычисляется** по файлам на диске — устареть
  он поэтому не может.
- Планировщик, исполнитель и проверщик включаются в свежий контекст **по
  отдельности**, и по умолчанию проверяет тот, кто не видел, как делали.

## Установка

```
/plugin marketplace add vefmvai/claude-plugins
/plugin install bpd@vefmvai
/reload-plugins
```

Посмотреть, ничего не устанавливая:

```
git clone https://github.com/vefmvai/big-project-done.git
claude --plugin-dir ./big-project-done
```

Обновление — `/plugin update bpd@vefmvai`.

### Если стоял BPD 1.x

Версия 1.x ставилась скриптом `install.sh`, который раскладывал файлы по четырём
папкам `~/.claude/`. Пока они там лежат, у вас **две копии команд `/bpd:*`**,
и какая сработает — вопрос везения. Уберите старую:

```bash
bash scripts/remove-legacy-install.sh
```

Скрипт показывает, что нашёл, и спрашивает подтверждение. Рабочие папки `.bpd/`
внутри ваших проектов он не трогает: **формат `.bpd/` не менялся, старые проекты
работают дальше без переделки.**

## Быстрый старт

```
/bpd:start    — рассказать Claude о проекте
/bpd:plan     — получить план первого этапа
/bpd:do       — выполнить этап
/bpd:check    — проверить результат
```

Дальше `plan → do → check` по кругу. Полный список команд — `/bpd:help`
или [`references/commands.md`](references/commands.md).

Пользовательская инструкция без технических деталей — [GUIDE.md](GUIDE.md).

## Как устроено

```
big-project-done/
├── .claude-plugin/plugin.json   манифест плагина
├── skills/                      7 команд /bpd:* — каждая целиком в одном файле
├── agents/                      3 субагента: planner, executor, checker
├── templates/                   шаблоны файлов проекта
├── references/
│   ├── rules.md                 общие правила: статусы, пути, нумерация, дома фактов
│   └── commands.md              справка /bpd:help
├── bin/bpd-validate             проверка папки .bpd/ — запускается и руками
├── hooks/                       автопрогон проверки и состояние на старте сессии
├── scripts/                     валидатор и уборка установки 1.x
└── tests/                       линтер плагина, тесты валидатора, живые прогоны
```

В каждом проекте после `/bpd:start` появляется:

```
.bpd/
├── PROJECT.md   что за проект, рамки, решения — только дописывается
├── ROADMAP.md   дорожная карта: этапы, цели, критерии готовности
├── STATE.md     история, проблемы, следующий шаг — перезаписывается
├── config.json  настройки
└── stages/NN-imya/  PLAN.md · RESULT.md · CHECK.md
```

## Три принципа, на которых всё держится

**1. Один факт — один дом.** Значение живёт в одном файле; остальные его читают.
Поэтому в `ROADMAP.md` нет колонки «Статус» (её никто не обновляет — она обречена
протухнуть), а в `STATE.md` нет решений (файл, который стирают, — плохой дом
для того, что терять нельзя).

**2. Статус вычисляется, а не объявляется.** Статус этапа выводится из файлов
в его папке:

Условия проверяются сверху вниз, первое совпадение выигрывает:

| Условие | Статус |
|---|---|
| этап в разделе «Отменённые» карты | ✗ Отменён |
| `CHECK.md`, в `## Итог` — «Принято» | ✓ Принят |
| `CHECK.md`, в `## Итог` — «Доработать» | ⚠ На доработке |
| `RESULT.md` | ● Выполнен |
| `PLAN.md`, хотя бы одна задача `[x]` | ◐ В работе |
| `PLAN.md`, ни одной `[x]` | ◎ Спланирован |
| `PLAN.md` нет | ○ Не начат |

Файлы создаёт сама работа, поэтому соврать они не могут. Отсюда жёсткое правило:
`RESULT.md` создаётся **только когда все задачи закрыты**.

**3. Номера этапов вечны.** Номер выдаётся один раз и не меняется никогда — он
записан в имени папки, в трёх файлах этапа и в истории. Перенумерация превратила
бы все эти записи в ссылки в никуда. Порядок выполнения задаёт порядок строк
в карте, а не номер, поэтому после правок номера могут идти вразнобой.

Полностью — [`references/rules.md`](references/rules.md). Это единственный дом
общих правил: команды его читают, а не пересказывают.

## Масштаб проекта

| Масштаб | Этапов | Как работает |
|---|---|---|
| Быстрый | 1–4 | план → выполнение, проверки нет |
| Средний | 5–14 | план и выполнение в текущем чате, проверка — свежим взглядом |
| Большой | 15 и больше | все три роли в свежем контексте |

## Свежий контекст — по ролям, а не одним рубильником

Свежий контекст даёт две разные вещи, и роли относятся к ним противоположно.
Проверщику независимость нужна: тот, кто делал работу, проверяет её слабо —
он помнит, как принимал решения, и защищает их вместо того, чтобы
перепроверять. Исполнителю та же свежесть выходит боком: он не видит человека
и спросить не может, а в интерактивном режиме об этом как раз просили.

Поэтому ролей три и флажков три:

```json
"use_subagents": {"plan": false, "do": false, "check": true}
```

Старая запись `true`/`false` тоже законна и означает «одинаково всем троим»,
так что проекты, созданные раньше, работают дальше без единой правки.

Масштаб задаёт умолчание, но не командует: проверщика можно включить на любом
проекте, а можно и выключить.

## Что проверяет машина

Правило, которое некому проверить, — это просьба, а не гарантия. Поэтому
у BPD есть валидатор: он читает `.bpd/` и говорит, где заявленное расходится
с тем, что на диске.

```
bpd-validate                 # в корне проекта
```

Двадцать три проверки. Пять главных ловят поломку статуса и прогресса, то есть
самой сути фреймворка: галочки, заехавшие в чеклист качества; вердикт, написанный
третьим словом; `RESULT.md`, созданный раньше времени; две папки на один номер;
файл, заявленный в отчёте, но отсутствующий на диске.

Валидатор **асимметричен намеренно**: ошибками он ловит только завышение доверия
— то, из-за чего проект выглядит здоровее, чем есть. Всё, что требует
человеческого суждения, идёт предупреждением и приговором не считается.

Три исхода, а не два:

| Код | Что значит |
|---|---|
| 0 | ошибок нет — заявленное непротиворечиво |
| 1 | найдены проблемы |
| 2 | **прогон не состоялся** — нечего проверять, не прочиталось, упало |

Код 2 существует затем, чтобы невыполненная проверка не выглядела как
пройденная. Молчание никогда не значит «всё хорошо».

Запускать вручную не обязательно: после каждой записи в `.bpd/` валидатор
прогоняется хуком сам. Когда всё чисто — молчит.

## Честные границы

Проект обязан говорить о себе то, что требует от чужих.

- **BPD не делает работу за вас и не проверяет содержание.** Он следит за формой:
  все ли задачи закрыты, все ли заявленные файлы на месте, пройден ли чеклист.
  Хороша ли глава по существу — решает человек на шаге `/bpd:check`.
- **«Принято» не значит «хорошо».** Это значит «сделано то, что обещал план».
  Если план был плохим, приёмка это не поймает — для этого есть `/bpd:update`.
- **Валидатор проверяет форму, а не смысл.** `exit 0` означает «заявленное
  непротиворечиво», а не «проект в порядке». Выдуманный факт, слабый текст
  и бессмысленный этап он пропустит: он видит файлы, а не работу.
- **Свежий контекст стоит денег.** Каждый запуск субагента заново читает правила,
  шаблон, `PROJECT.md` и карту — около 26 КБ, примерно шесть-девять тысяч
  токенов, и это только пол: дальше добавляются `RESULT.md` прошлых этапов,
  которые растут вместе с проектом. Ради этого субагент и существует, но платить
  приходится каждый раз.
- **Нет отката.** `/bpd:check` при вердикте «Принято» предложит сделать коммит
  и покажет, что в него войдёт, но откатывать неудачный этап придётся самому,
  обычными средствами git. Отменять чужие изменения вслепую опаснее, чем
  оставить их на месте.
- **Windows не поддерживается.** Проверить эту работу не на чем, и делать вид,
  что «просто не проверяли», нечестно: валидатор и хуки запускаются через bash
  и `python3`.
- **Linux не проверялся.** Запускаемого кода немного, и переносимость соблюдена
  осознанно — bash без версионных изысков, python3 без внешних библиотек, —
  но прогона на Linux не было.
- **Проверено на macOS**, включая родной bash 3.2, а не только на свежем.

## Как это проверяется

Три набора, по возрастанию доверия и цены:

```
python3 tests/lint-plugin.py     секунда, бесплатно
   → репозиторий плагина не сгнил от правок

bash tests/run-tests.sh          секунды, бесплатно
   → валидатор ловит все свои поломки и не ловит лишнего

bash tests/run-live.sh           минуты, тратит токены
   → команды действительно делают то, что обещают
```

Первые два гоняются после любой правки. Третий — перед выпуском версии: он
запускает настоящий Claude без окна на одноразовой копии проекта и смотрит,
что получилось на диске. Дорого, зато врать не умеет: три худших бага августа
2026 нашёл именно такой прогон, а не чтение файлов глазами.

Тесты живут рядом с плагином намеренно: тот, кто клонировал репозиторий, должен
мочь прогнать их сразу, не собирая ничего вокруг.
