# /bpd:check — проверить этап

Проверка нужна не для отчётности. Она ловит расхождение между тем, что написано
в `RESULT.md`, и тем, что на самом деле лежит на диске.

## Что прочитать перед работой

1. `${CLAUDE_PLUGIN_ROOT}/references/rules.md`
2. `${CLAUDE_PLUGIN_ROOT}/templates/CHECK.md`

## Шаг 1. Найти этап

Номер передан в `$ARGUMENTS` (может быть пустым).

- **Номер есть** → работаем с ним.
- **Номера нет** → взять **первый** по порядку карты этап со статусом
  «Выполнен» (●) по `rules.md` § 3 — то есть `RESULT.md` есть, `CHECK.md` нет.
  Первый, а не последний: `/bpd:plan` и `/bpd:do` без номера тоже берут первый
  подходящий, и три команды цикла обязаны выбирать одинаково.
- **Таких нет** → сказать: «Нет выполненных этапов для проверки.» Остановиться.

Папку искать глобом `.bpd/stages/NN-*`.

## Шаг 2. Прочитать контекст

- `[папка этапа]/PLAN.md` — задачи и чеклист качества;
- `[папка этапа]/RESULT.md` — что заявлено сделанным;
- `.bpd/ROADMAP.md` — критерии готовности этапа;
- `.bpd/config.json` — `use_subagents`.

## Шаг 3. Машинная проверка

### Если `use_subagents: false`

Проверить здесь же, пять вещей:

1. **Задачи.** Посчитать `[x]` и `[ ]` в `PLAN.md`. Незакрытые — назвать поимённо.
2. **Задачи с пометкой `⚠️`** (признаны невыполнимыми) — отдельно: есть ли каждой
   объяснение в `RESULT.md`, в разделе «Отклонения от плана» или «Проблемы».
   Молча пропущенная задача выглядит как выполненный этап.
3. **Файлы.** Взять список файлов из `RESULT.md` и проверить каждый на диске
   (`test -e`). Заявлен, но отсутствует — это провал проверки, а не мелочь.
4. **Чеклист качества.** Пройти каждый пункт из `PLAN.md`, **глядя в сами файлы**,
   а не в описание результата.
5. **Критерии готовности** из `ROADMAP.md` — оценить каждый.

### Если `use_subagents: true`

Запустить проверщика в свежем контексте — он не видел работы и потому не будет
защищать её. Пути настоящие и абсолютные (`rules.md` § 9).

```
Task(
  subagent_type: "bpd:checker",
  description: "Проверка этапа N",
  prompt: """
  Проверь результат этапа проекта BPD.

  Этап: N — [Название]
  Папка этапа: [абсолютный путь к .bpd/stages/NN-imya]
  Корень проекта: [абсолютный путь]

  Прочитай в таком порядке:
  1. ${CLAUDE_PLUGIN_ROOT}/references/rules.md   — общие правила BPD
  2. ${CLAUDE_PLUGIN_ROOT}/templates/CHECK.md    — шаблон отчёта проверки
  3. [папка этапа]/PLAN.md                       — задачи и чеклист качества
  4. [папка этапа]/RESULT.md                     — что заявлено сделанным
  5. [путь]/.bpd/ROADMAP.md                      — критерии готовности этапа

  RESULT.md — это заявление, а не доказательство. Проверяй файлы на диске.

  Создай [папка этапа]/CHECK.md по шаблону.
  В разделе «## Итог» — ровно «Принято» или «Доработать», без синонимов:
  оттуда берётся статус этапа.
  """
)
```

Вернулся — прочитать `CHECK.md` самому.

## Шаг 4. Проверка человеком

Машина видит, что файл есть. Хорош ли он — видит только человек.

Показать чеклист качества из `PLAN.md` и спросить:

```
AskUserQuestion:
  header: "Проверка"
  question: "Все критерии качества выполнены?"
  options:
    - label: "Да, всё в порядке"  description: "Этап принят"
    - label: "Есть замечания"     description: "Нужны доработки"
```

Если «Есть замечания» — попросить описать их словами и записать дословно.

**Если спросить некого** — запуск неинтерактивный, диалога нет, ответ получить
неоткуда — **не останавливаться и не ждать.** Написать в разделе «Проверка
человеком»: «Не проводилась — сессия без диалога», вынести вердикт по одним
машинным проверкам и в итоге сказать, что содержательную часть человек не
смотрел и может перепроверить, запустив `/bpd:check N` ещё раз.

Остановка здесь — худший исход из возможных: `CHECK.md` не появляется вовсе,
этап остаётся без статуса, и снаружи это неотличимо от «проверка не
запускалась». Отчёт без человеческой части честнее, чем отсутствие отчёта.

## Шаг 5. Записать CHECK.md

Создать `[папка этапа]/CHECK.md` по шаблону, если его ещё не создал субагент,
или дополнить результатами проверки человеком.

**В разделе `## Итог` стоит одно из двух слов — «Принято» или «Доработать».**
Оттуда `/bpd:status` берёт статус этапа (`rules.md` § 3). Любое другое слово
оставит этап без статуса вовсе.

Правило вердикта: хоть один невыполненный пункт чеклиста, хоть один заявленный,
но отсутствующий файл, хоть одно замечание человека — «Доработать».

## Шаг 6. Обновить STATE.md

Дописать в историю: «Этап N принят» или «Этап N отправлен на доработку».
Замечания — в раздел «Проблемы». Обновить «Следующий шаг»: `/bpd:plan`
при приёмке, `/bpd:do N` при доработке.

Статус и процент в `STATE.md` не записывать.

## Шаг 7. Предложить точку отката

Только при вердикте «Принято» и только если проект в git (`.git` в корне).
Подробности — `rules.md` § 8.

Проверить `git status --porcelain`. Если менять нечего — молча пропустить шаг.

Если есть что коммитить — **показать, что именно, и спросить**:

```
Этап [N] принят. Сделать точку отката?

Изменений: [сколько] файлов
Сообщение: BPD этап [N]: [Название] — принят

[да / нет / посмотреть список]
```

Согласился — `git add -A && git commit`. Отказался — идти дальше молча
и больше не переспрашивать.

**Сам не коммитить.** Это чужой репозиторий: там может быть недоделанная
работа, чужая ветка, свои правила сообщений. Незваный коммит чинить дороже,
чем не сделать его вовсе.

## Самопроверка

- [ ] Этап найден, `PLAN.md` и `RESULT.md` прочитаны
- [ ] Каждый заявленный файл проверен на диске
- [ ] Чеклист качества пройден по файлам, а не по описанию
- [ ] Человек посмотрел результат и высказался
- [ ] `CHECK.md` создан, итог — ровно «Принято» или «Доработать»
- [ ] `STATE.md` дополнен, следующий шаг назван
- [ ] При «Принято» в git-проекте точка отката предложена, а не сделана молча
